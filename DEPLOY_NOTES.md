## 2026-09-25 — описания malformed JSON во всех endpoint'ах Swagger

- Запрос пользователя: при следующем деплое убрать из Swagger описания и примеры ошибки синтаксически некорректного JSON (`malformedJson`, `malformed JSON` и аналогичные) во всех endpoint'ах, где они присутствуют, а не только у регистрации. Пользователь считает этот сценарий неактуальным для текущих автотестов.
- Контекст: текущий endpoint-клиент принимает Pydantic-модель и отправляет её через `json=`. Изменение значения поля не позволяет сформировать синтаксически некорректный JSON. Для такого запроса необходима передача сырого тела через `content`.
- Техническое замечание: ограничение тестового клиента не делает ошибку API недействительной. Некорректный синтаксис JSON действительно может привести к `400`; нарушение ограничений полей корректного JSON — к `422`.
- При следующем деплое проверить все операции и общие компоненты OpenAPI: убрать указанные примеры и упоминания сломанного синтаксиса JSON, включая описания с несколькими причинами ошибки. Сохранить остальные документированные причины ответа `400`, в частности `missingBody`. Удаление примеров из Swagger не должно удалять обработку некорректного JSON на сервере; фактический ответ сервера на такой запрос остаётся возможным.
- Статус: реализовано 2026-10-02; обработка ошибок сервера сохранена.

## 2026-09-26 — уточнение конфликтующего поля при регистрации

- Тип: доработка ответа `409 USER_ALREADY_EXISTS`.
- Сейчас при занятом username или email сервер возвращает общее сообщение и `details: []`. Из ответа нельзя определить, какое поле вызвало конфликт.
- Требуемое поведение: заполнять `details` элементами `field` / `message` для конфликтующих полей `username` и/или `email`. Само переданное значение email или username в ответе дублировать не требуется.
- Сохранить HTTP-статус `409` и код `USER_ALREADY_EXISTS`; описать уточнения и примеры в OpenAPI.
- При реализации проверить отдельно занятый email, занятый username и конфликт обоих полей, включая обработку конфликта уникальности при параллельной регистрации.
- Это не общий дефект `details`: список уже заполняется для ошибок валидации полей и `PROFILE_INCOMPLETE`.
- Статус: реализовано 2026-10-02.

## 2026-10-02 — удалить CONFIRMATION_STATE_CHANGED

- Запрос пользователя: удалить отдельную ошибку `409 CONFIRMATION_STATE_CHANGED` из API и Swagger для подтверждения регистрации и повторной отправки ссылки.
- Причина: описание «состояние ссылки изменилось» не даёт понятного сценария для пользователя API; воспроизводимый сценарий получения этой ошибки пока не установлен. Это не доказательство недостижимости ветки — её условия нужно проверить при реализации.
- При реализации пересмотреть конкурентное обновление подтверждения в AuthService и UserData. Сохранить защиту от повторного использования и заменённых ссылок; определить результат неуспешного обновления по актуальному состоянию пользователя и ссылки. Не заменять удаляемую ошибку безусловным успехом или необработанным исключением с ответом 500.
- Сохранить существующие понятные сценарии: повторное подтверждение — `409 ACCOUNT_ALREADY_CONFIRMED`, невалидная или заменённая ссылка — `400 INVALID_CONFIRMATION_LINK`, истёкшая ссылка — `410 CONFIRMATION_LINK_EXPIRED`, отсутствующий пользователь — `404 USER_NOT_FOUND`.
- Удалить соответствующие примеры `stateChanged` и формулировки из всех затронутых операций OpenAPI; привести проверки в соответствие с новым поведением, включая конкурентные подтверждение и перевыпуск ссылки.
- Статус: реализовано 2026-10-02; публикация выполняется через стандартный GitHub Docker workflow.
