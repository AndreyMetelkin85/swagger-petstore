# Проверки и доставка учебного магазина

## Маршруты изменений

Классификация выполняется относительно последнего `master`, у которого успешно завершился publishing job. Это важно при нескольких быстрых push: документация после ещё не выпущенной правки API не может отменить необходимые проверки этой правки. Если baseline недоступен, CI выбирает полный прогон.

| Изменение | Проверки | Публикация |
| --- | --- | --- |
| Документация, неизменённый перенос master → dev | Классификация | Нет |
| UI или фотографии | Unit, TypeScript, native AMD64/ARM64, API/SMTP, фотографии, безопасность | Из проверенных digests |
| API, конфигурация, зависимости, миграции, тесты, неизвестные файлы | Дополнительно полный backend, Swagger, почта, перезапуск/обновление и постоянные данные | После всех проверок |

Pull request не получает Docker Hub credentials и не публикует образ: полный набор запускается на изолированном локальном candidate. Производственный выпуск выполняется на push в master. Устаревшие запуски отменяются; перед promotion CI проверяет текущий HEAD master.

## Одна сборка, параллельные проверки

- BuildKit cache разделён по архитектурам. ARM64 выполняется на `ubuntu-24.04-arm`; эмулируется только upstream amd64-слой инструментов Flyway.
- Образ приложения собирается один раз. `candidate-*` — непроверенные промежуточные теги; использовать их для учебного стенда не нужно.
- Regression и system/UI выполняются параллельно на одном и том же candidate digest.
- Unit и integration выполняются один раз в четырёх процессах. Каждый integration worker получает собственную `petstore_python_test_gwN`, созданную и мигрированную отдельно. Пароли и параметры bcrypt приложения не упрощаются.
- Парсинг OpenAPI безопасным загрузчиком кэшируется по пути, размеру и времени изменения файла; каждому приложению выдаётся независимая копия документа.
- Порог покрытия 90%, существующие проверки заказов, платежей, почты, фото и сохранения данных остаются обязательными.
- `latest` перемещается только после успешных gates: promotion объединяет протестированные AMD64 и ARM64 manifests без повторной сборки, сохраняя SBOM/provenance.
- OS-зависимости обновляются с дневным cache epoch, базы сканера кэшируются. Полная проверка также доступна через workflow_dispatch и недельный schedule.

Длительность зависит от очереди runner и холодного кэша. Сравнивать нужно критический путь workflow, а не сумму параллельных jobs; pytest печатает двадцать наиболее долгих тестов. Первое наполнение кэша не является замером тёплого цикла.

## Измеренный результат

Первый полный выпуск нового pipeline: [GitHub Actions, 8 октября 2026](https://github.com/AndreyMetelkin85/swagger-petstore/actions/runs/37811516283), **10 минут 58 секунд** от создания run до успешного завершения. Предыдущий полный выпуск занимал около 29 минут 28 секунд. Это замер CI, не всего времени разработки.

413 unit/integration тестов прошли за 108,44 секунды, покрытие 94,53%. Ранее regression занимал около 11 минут, а unit запускался ещё и отдельно. ARM64 job сократился примерно с 9 минут 56 секунд до 4 минут 40 секунд. Проверки Swagger, почты, перезапуска, сохранения данных, фотографии и 11 API/UI сценариев также прошли. Публикация использовала готовые digests без пересборки.

Время тёплого выпуска и небольшого UI hotfix отдельно пока не измерено; обещать для них точную длительность нельзя. Для UI/фото остаются контрактные и браузерные проверки, но не повторяется полный backend regression и Swagger.

## Обновление стенда

Из корня проекта:

```powershell
.\docker\update-store.ps1
```

Скрипт скачивает проверенный latest, проверяет revision и запускает Compose без сборки. Совпадающий здоровый контейнер остаётся работающим. `.env`, JWT secret, база, фотографии и письма сохраняются.

Для выбора ранее выпущенной совместимой версии:

```powershell
.\docker\update-store.ps1 -Tag sha-<полный-коммит>
```

Это выбор версии приложения, не откат миграций БД. Схема должна оставаться совместимой с выбранной версией. Скрипт не удаляет volumes и не выполняет автоматический downgrade.
