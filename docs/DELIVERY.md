# Проверки и доставка учебного магазина

## Маршруты изменений

Классификация выполняется относительно последнего `master`, у которого успешно завершился publishing job. Это важно при нескольких быстрых push: документация после ещё не выпущенной правки API не может отменить необходимые проверки этой правки. Если baseline недоступен, CI выбирает полный прогон.

| Изменение | Проверки | Публикация |
| --- | --- | --- |
| Документация, неизменённый перенос master → dev | Классификация | Нет |
| UI или фотографии | Unit, TypeScript, native AMD64/ARM64, API/SMTP, фотографии, безопасность | Из проверенных digests |
| API, конфигурация, зависимости, миграции, тесты, неизвестные файлы | Дополнительно полный backend, Swagger, почта, перезапуск/обновление и постоянные данные | После всех проверок |

Pull request не получает Docker Hub credentials и не публикует образ: полный набор запускается на изолированном локальном candidate. Производственный выпуск выполняется на push в master. Устаревшие запуски отменяются; перед promotion CI проверяет текущий HEAD master.

## Одна сборка, параллельные проверки

- BuildKit registry cache (`mode=max`) разделён по архитектурам и веткам: `buildcache-master-*` и `buildcache-dev-*`. Dev читает master cache, но не перезаписывает его. ARM64 выполняется на `ubuntu-24.04-arm`; эмулируется только upstream amd64-слой инструментов Flyway.
- Образ приложения собирается один раз. `candidate-*` — непроверенные промежуточные теги; использовать их для учебного стенда не нужно.
- AMD64 и ARM64 собираются независимыми jobs. Regression, Swagger и system/UI начинают работу после готовности AMD64 digest, не ожидая ARM64 или сканеров. Каждый job имеет отдельный стенд.
- Проверки с перезапуском/обновлением внутри system job выполняются последовательно; Swagger проверяет все операции одним браузером и закрывает уже проверенные формы.
- Contracts/commerce и Trivy проверяют точные digests обеих архитектур параллельно с остальными jobs. Публикация ожидает все необходимые gates.
- Unit и integration выполняются один раз в четырёх процессах. Каждый integration worker получает собственную `petstore_python_test_gwN`, созданную и мигрированную отдельно. Пароли и параметры bcrypt приложения не упрощаются.
- Парсинг OpenAPI безопасным загрузчиком кэшируется по пути, размеру и времени изменения файла; каждому приложению выдаётся независимая копия документа.
- Порог покрытия 90%, существующие проверки заказов, платежей, почты, фото и сохранения данных остаются обязательными.
- `latest` перемещается только после успешных gates: promotion объединяет протестированные AMD64 и ARM64 manifests без повторной сборки, сохраняя SBOM/provenance.
- OS-зависимости обновляются с дневным cache epoch. Trivy выполняется от UID/GID runner с каталогом `/cache`: базы и результаты анализа читаются runner и сохраняются actions/cache. Обновление базы уязвимостей не отключается. Полная проверка также доступна через workflow_dispatch и недельный schedule.

Длительность зависит от очереди runner и холодного кэша. Сравнивать нужно критический путь workflow, а не сумму параллельных jobs; pytest печатает двадцать наиболее долгих тестов. Первое наполнение кэша не является замером тёплого цикла.

## Измеренный результат

Первый этап ускорения, полный выпуск: [GitHub Actions, 8 октября 2026](https://github.com/AndreyMetelkin85/swagger-petstore/actions/runs/37811516283), **10 минут 58 секунд** от создания run до успешного завершения. Предыдущий полный выпуск занимал около 29 минут 28 секунд. Это замер CI, не всего времени разработки.

413 unit/integration тестов прошли за 108,44 секунды, покрытие 94,53%. Ранее regression занимал около 11 минут, а unit запускался ещё и отдельно. ARM64 job сократился примерно с 9 минут 56 секунд до 4 минут 40 секунд. Проверки Swagger, почты, перезапуска, сохранения данных, фотографии и 11 API/UI сценариев также прошли. Публикация использовала готовые digests без пересборки.

Второй этап ускорения, 8 октября 2026:

| Прогон | Полный run | Результат |
| --- | --- | --- |
| [Первый успешный выпуск](https://github.com/AndreyMetelkin85/swagger-petstore/actions/runs/37816133983) | 6 мин 42 с | 443 теста, покрытие 94,51%, обе архитектуры и все gates, публикация |
| [Повторный полный прогон](https://github.com/AndreyMetelkin85/swagger-petstore/actions/runs/37817098359) | 5 мин 35 с | Все gates зелёные, registry и Trivy cache восстановлены; manual run не публикует повторно |
| [Финальный выпуск](https://github.com/AndreyMetelkin85/swagger-petstore/actions/runs/37818080971) | 6 мин 10 с | 444 теста, покрытие 94,51%, все gates и публикация; отдельные cache timings подтверждены автоматически |

Первый run включал 64 секунды до старта классификации, пока отменялся предыдущий запуск. До завершения gates/promotion прошло 390 секунд; до полного завершения run, включая timing job, — 402 секунды. Поэтому время очереди и время выполнения указаны отдельно.

AMD64 build job занял 68 секунд (BuildKit build/push/cache — 31 с, загрузка точного digest — 12 с). Registry cache export: AMD64 6,9 с, ARM64 4,8 с. Полный Swagger в Linux: 34,32 с. В первом выпуске unit/integration заняли 174,85 с, в повторном — 194,74 с; длительность этого этапа на бесплатных runners варьируется. Именно backend regression теперь определяет основной критический путь.

В финальном выпуске registry cache export составил 4,6 с для AMD64 и 4,7 с для ARM64; полный Swagger прошёл за 27,34 с, unit/integration — за 138,42 с. С восстановленным Trivy cache сканирование в повторном прогоне заняло 10–15 с.

Timing summary показывает очередь каждого job, сборку, экспорт registry cache, тесты и promotion. Время до завершения gates/promotion приводится отдельно от служебного timing job; длительности параллельных jobs не суммируются.

Цель полного тёплого цикла до 7 минут выполнена на измеренных прогонах. Небольшой UI hotfix отдельно пока не измерен; ориентир до 4 минут не считается подтверждённым. Для UI/фото остаются контрактные и браузерные проверки, но не повторяется полный backend regression и Swagger.

## Обновление стенда

Из корня проекта:

```powershell
.\docker\update-store.ps1
```

Скрипт скачивает проверенный latest, проверяет revision и запускает Compose без сборки. Совпадающий здоровый контейнер остаётся работающим. `.env`, JWT secret, база, фотографии и письма сохраняются.

Для выбора ранее выпущенной совместимой версии:

```powershell
.\docker\update-store.ps1 -Tag sha-<полный-коммит>
```

Это выбор версии приложения, не откат миграций БД. Схема должна оставаться совместимой с выбранной версией. Скрипт не удаляет volumes и не выполняет автоматический downgrade.
